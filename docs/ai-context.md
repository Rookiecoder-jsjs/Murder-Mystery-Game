# AI 角色的知识、证言与上下文

[返回项目首页](../README.md) · [开发指南](development.md)

本文说明当前实现的资料边界与回复检查。真实模型表现及已知问题见 [首批真机实玩记录](builtin-story-playthrough.md)，不能把程序检查通过理解为模型永远不会幻觉。

## 角色能知道什么

`ContextAssembler` 先按权限筛选，再选择相关历史。角色可见公开案情、自己的 `self_knowledge` 与 `objectives`、已获得或已公开的线索，以及有权访问的证言。其他人物只提供公开身份；作者真相、完整秘密与 `solution` 不进入正常扮演请求。

`cover_story` 是作者允许的对外说辞，单独保存，不等于本人真实经历。文书、证词和角色发言保留来源类别，不因模型推理、摘要或反复引用升级为客观事实。定向询问仍属于公共讨论，出示证据后所有角色可见。

一次玩家行动中的所有角色使用同一事件序号的冻结快照。本轮其他角色的回复在下一次行动才可见，避免并发完成顺序改变角色知识。

## 如何组织上下文

固定规则放在系统消息，资料与发言作为数据提供；当前问题只出现一次。序列化按以下顺序组织：

1. 公共案情、本人资料与玩家身份。
2. 可见线索及按原始时间顺序排列的证言。
3. 当前阶段、轮次、公开证据 ID 和引用白名单。
4. 本次问题。

工具定义不随候选人、来源或轮次变化，权限由后端再次检查。线索公开时只更新末尾公开状态，不重写正文；不同角色的私密资料不共享。

历史在预算允许时完整保留，新发言追加在后。超出预算时，从权威事件日志确定性选取相关原话、重要证言与近期对话，仍保持原始顺序；更正和原话一起提供，不生成无来源的事实摘要。预算按 UTF-8 字节保守估算，必要案情、本人知识和可见线索不被静默截断。

## 回复为什么需要检查

模型通过 `submit_statement.segments` 提交分句及来源，后端拼接唯一正文，并检查来源可见性、陈述类别、明确时间和更正归属。独立事实审查覆盖全部分句，不能以文书直接证明本人行动，也不能将两个分离时点拼成连续在场区间。

不合格草稿最多修复一次，不写入正式事件或长期记忆。仍失败时优先返回与问题相关的本人原文或可见证据；凶手回退只使用允许的对外说辞。可选表决意见检查失败则弃权。检查通过后才推送和保存，可能增加回复延迟，也仍不能排除所有自然语言错误。

## 存档与剧本制作

`discussion_events` 是权威对话记录，`discussion_history` 是兼容投影。恢复时从权威状态确定性重建上下文，不维护第二份独立 AI 记忆。旧记录缺失的阶段和轮次保持缺省，不推断补造。

会话快照 schema 4 冻结完整剧本正文和版本，内容更新不会改变已开始的游戏。新剧本在制作阶段完成结构、证据可达性与语义检查后保存；成品开局、继续存档和基础复盘只做本地操作，不补做在线审稿，也不为旧内容伪造审稿证明。

## 缓存如何验证

稳定前缀增加供应商复用的机会，不能保证命中。缓存命中以供应商实际 `usage` 为准；`context.cache_prefix_sha256` 只检查前缀变化，不是缓存键或命中证明。缺少供应商指标时记录 `null`，不计作零命中。

在 `backend/` 执行可查看按模型、游戏、角色和阶段汇总的 token 加权统计：

```bash
python -m app.core.prompt_cache --game-id '<游戏ID>'
# 或指定追踪文件
python -m app.core.prompt_cache 'logs/llm/<日期>.jsonl'
```

统计区分 `reported_calls` 与 `unknown_calls`。追踪日志可能包含游戏内容，分享排障信息前应检查数据范围；配置见 [环境模板](../backend/.env.simple)。
